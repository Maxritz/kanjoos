# Worksheet — C19 CPU / direct-memory expert fallback

**What it owns:** the escape hatch when an expert will not arrive in time.

**Why it exists (from `02-components.md` — C19 section; `01` §6):** the central observation from Fiddler: the activation tensor is far smaller than the expert weights, so for small batches it can be cheaper to compute a missing expert on the CPU than to move it over PCIe.
Enabled when `batch_tokens <= threshold` **and** the expert is not resident **and** predicted transfer cost exceeds CPU cost. With ReBAR on, the warm pool can be mapped into the GPU address space as a last-resort direct-access path — still PCIe-bound per access, so it belongs here, never in attention. Must not block unrelated GPU work and must not mutate the canonical representation.

**Spec lines that must hold:**
* `02-components.md` — C19 section (verbatim: the Fiddler observation; the `FallbackCost { transfer_us, cpu_us, prefer_cpu }` struct and `estimate()` API; the enable condition (batch_tokens <= threshold AND not resident AND predicted transfer cost exceeds CPU cost); the ReBAR direct-access path (still PCIe-bound per access, belongs here never in attention); must not block unrelated GPU work and must not mutate the canonical representation; done-when).
* `01-architecture.md` §6 (control flow: on a missing expert, the scheduler has already either found it in RAM and issued H2D early enough, found it in NVMe and issued the read early enough, or failed to and taken the CPU/expert fallback (C19) rather than stalling. A hard stall is a last resort and a telemetry event (STALL_TIME_MS), never the mechanism. C19 is the fallback that avoids the stall.)
* `04-memory-tiering.md` §1 (ReBAR enables host-mapped warm memory as a legitimate last-resort path in C19 — a kernel can read a warm expert over the BAR without a staging copy — but it is still PCIe latency per access, so it belongs in the expert fallback, never in attention.)
* `04-memory-tiering.md` §5.1 (the discipline: the attention path never issues a storage read; if a required page is not in VRAM when its layer arrives, the scheduler has already either found it in RAM and issued H2D early enough, found it in NVMe and issued the read early enough, or failed to and taken the CPU/expert fallback (C19) rather than stalling. C19 is the fallback that avoids the stall.)
* `09-kv-engine-architecture.md` §5 (I1: no expert is ever lost — every routed expert is recoverable from RAM or NVMe; a cache miss changes latency, never the result. C19 is the mechanism that makes "a cache miss changes latency, never the result" true when the expert is not in VRAM and will not arrive in time: instead of stalling, compute it on the CPU (or read it over the BAR if ReBAR is on). The result is the same — the expert's contribution is accumulated — but the latency path is CPU compute (or BAR read), not a stall.)

**Interface (verbatim `02-components.md` C19):**
```cpp
struct FallbackCost { uint64_t transfer_us, cpu_us; bool prefer_cpu; };
FallbackCost estimate(ExpertId, uint32_t batch_tokens);
```

**Rules (verbatim):**
* Enabled when `batch_tokens <= threshold` **and** the expert is not resident **and** predicted transfer cost exceeds CPU cost.
* With ReBAR on, the warm pool can be mapped into the GPU address space as a last-resort direct-access path — still PCIe-bound per access, so it belongs here, never in attention.
* Must not block unrelated GPU work and must not mutate the canonical representation.

**Acceptance test (verbatim "done when"):**
* On a 6 GiB profile, cold-expert requests complete within the latency SLO instead of stalling.
* The CPU-fallback counter in telemetry is the thing that tells you whether the predictor is good enough.

**Coder notes / pitfalls:**
* The Fiddler observation is the core idea: the activation tensor is far smaller than the expert weights, so for small batches it can be cheaper to compute a missing expert on the CPU than to move it over PCIe. A coder must implement the cost model as a real comparison (transfer_us vs cpu_us), not as "always CPU" or "always transfer". The `FallbackCost { transfer_us, cpu_us, prefer_cpu }` struct is the interface — `estimate()` returns both costs and the boolean. A coder must compute `transfer_us` from the actual transfer path (NVMe→RAM→H2D, or RAM→H2D, or BAR read) and `cpu_us` from the actual CPU compute cost (the gate/up/down GEMM for the missing expert, for the batch tokens that route to it), and set `prefer_cpu` when `cpu_us < transfer_us`. A coder must not hardcode "CPU fallback is always better for small batches" — the threshold is a function of batch_tokens, the transfer cost, and the CPU cost, and it must be measured (C21 reports the CPU-fallback counter, which is the signal that tells you whether the predictor is good enough).
* Enable condition: `batch_tokens <= threshold` AND not resident AND predicted transfer cost exceeds CPU cost. All three must hold. A coder must not fall back to CPU when the expert is resident (that would recompute a resident expert — wrong and wasteful — the resident expert is read from VRAM by C17, not recomputed by C19). A coder must not fall back to CPU when the transfer will arrive in time (that would recompute an expert that was going to be resident in time — wasteful — the planner (C9/C10/C11) has already arranged the transfer; C19 is the fallback when the planner has determined it will not arrive in time). A coder must not fall back to CPU for large batches (the activation tensor grows with batch_tokens, so CPU cost grows; the threshold is where CPU cost exceeds transfer cost — A coder must measure this and set the threshold, not assume a value).
* ReBAR direct-access path: with ReBAR on, the warm pool can be mapped into the GPU address space as a last-resort direct-access path — a kernel can read a warm expert over the BAR without a staging copy — but it is still PCIe-bound per access, so it belongs here, never in attention. A coder must implement the BAR read as a special case (no staging copy — the GPU reads the warm expert directly from the host-mapped warm pool), but must not treat it as "fast" — it is still PCIe latency per access (the warm expert is in host RAM, mapped into the GPU address space via ReBAR; the GPU reads it over PCIe, one access at a time, with PCIe latency per access — no staging copy, but no bandwidth advantage either; it is a latency-bound, per-element read, which is fine for a small activation tensor computed by the GPU, but it is NOT a way to feed a large GEMM). A coder must not put a BAR read in the attention path (that is the "belongs here, never in attention" rule — the BAR read is a last-resort expert-fallback path, not an attention path). A coder must not assume ReBAR is on — C24's doctor reports ReBAR state, and the BAR read is conditional on ReBAR being on; if ReBAR is off, the fallback is the normal transfer path (NVMe→RAM→H2D) or CPU compute, not a BAR read.
* Must not block unrelated GPU work. A coder must implement the CPU fallback so it does not block unrelated GPU work — the CPU compute for the missing expert is done on the CPU (or, if the GPU is going to compute it, the GPU computes it from the BAR-read or staging-copied weights, but the point is the expert's contribution is computed and accumulated without stalling the rest of the GPU work). A coder must not stall the whole GPU waiting for the CPU to compute the missing expert — the CPU fallback is for the missing expert's contribution only, and it is accumulated into the residual; the rest of the batch's GPU work (other experts, attention, other layers) continues. A coder must not make the CPU fallback a "stop the world" operation.
* Must not mutate the canonical representation. A coder must implement the CPU fallback so it does not mutate the canonical representation — the CPU computes the missing expert's contribution (gate/up/down GEMM) and accumulates it into the token's residual; it does not write back to the canonical expert weights (C5/C6) or to the resident slot (C8) — the canonical representation is unchanged. A coder must not have the CPU fallback modify the expert weights in the warm pool or on NVMe or in VRAM — that would mutate the canonical representation, which is forbidden. The fallback computes the contribution, not a new weight.
* The CPU-fallback counter is the thing that tells you whether the predictor is good enough. A coder must instrument the CPU-fallback counter (C21) and must not treat it as a failure counter — a high CPU-fallback counter is a signal that the predictor (C10) is not predicting well enough (too many experts are not ready in time, so the fallback is used too often), not that the fallback is bad. The fallback is the escape hatch; the counter tells you how often you need the escape hatch, which is the predictor-quality signal. A coder must not aim to minimise the CPU-fallback counter by disabling the fallback — the fallback is the thing that keeps cold-expert requests from stalling on a 6 GiB profile; the counter is the signal to tune the predictor (C10) and the prefetch/horizon (C10/C22), not to disable the fallback.
* The 6 GiB profile is the acceptance-test profile. A coder must run the acceptance test ("on a 6 GiB profile, cold-expert requests complete within the latency SLO instead of stalling") on a 6 GiB profile, because that is where cold-expert requests are common (the expert bank does not fit in VRAM at 6 GiB — `04` §2.1 — so cold experts are the common case, and the fallback is most valuable there). A coder must not run the acceptance test on a 16 GiB profile and conclude the fallback is unnecessary — at 16 GiB with W3 (the operating point, 126/128 experts resident), cold experts are rare (2/128 miss rate, ~0.2 ms/token — `ai-coder/operating-point.md`), and the fallback is less valuable; the 6 GiB profile is the one where the fallback matters. A coder must run the acceptance test where it matters.

**Worked micro-example (host, sanity-check before device):**
Implement a fake C19 with the `FallbackCost { transfer_us, cpu_us, prefer_cpu }` struct and `estimate(ExpertId, batch_tokens)` API, the enable condition (batch_tokens <= threshold AND not resident AND predicted transfer cost > CPU cost), the ReBAR BAR-read path (conditional on ReBAR being on and the expert being in the warm pool — no staging copy, but PCIe-bound per access), and the "must not block unrelated GPU work" and "must not mutate canonical representation" rules. Then: (1) implement `estimate()` to compute `transfer_us` from the actual transfer path (NVMe→RAM→H2D, or RAM→H2D, or BAR read) and `cpu_us` from the actual CPU compute cost (the missing expert's gate/up/down GEMM for the batch tokens that route to it), and set `prefer_cpu` when `cpu_us < transfer_us` — and assert the enable condition holds (batch_tokens <= threshold AND not resident AND transfer_us > cpu_us) before falling back — the "enable condition all three hold" gate; (2) assert the CPU fallback computes exactly what C17 would have computed for the missing expert (same expert, same tokens, same weights — gate/up/down GEMM, same accumulation into the residual) — the "computes what C17 would have computed" gate; (3) assert the CPU fallback does not mutate the canonical representation (the expert weights in C5/C6, the warm pool, the VRAM slot are unchanged) — only the token's residual is updated with the missing expert's contribution — the "must not mutate canonical representation" gate; (4) assert the CPU fallback does not block unrelated GPU work (the CPU computes the missing expert's contribution and accumulates it; the rest of the batch's GPU work continues) — the "must not block unrelated GPU work" gate; (5) implement the ReBAR BAR-read path: with ReBAR on and the expert in the warm pool, the GPU reads the warm expert directly from the host-mapped warm pool (no staging copy), but it is still PCIe-bound per access — and assert the BAR read is a last-resort expert-fallback path, not an attention path, and that it is conditional on ReBAR being on (C24's doctor reports ReBAR state) — the "BAR read is expert-fallback-only, conditional on ReBAR, still PCIe-bound per access" gate; (6) implement the CPU-fallback counter (C21) and assert it is the signal that tells you whether the predictor is good enough (a high counter means the predictor (C10) is not predicting well enough — too many experts not ready in time — not that the fallback is bad) — the "CPU-fallback counter is predictor-quality signal" gate; (7) run the acceptance test on a 6 GiB profile (the profile where cold-expert requests are common) and assert cold-expert requests complete within the latency SLO instead of stalling — the "cold-expert requests complete within SLO on 6 GiB" gate; (8) assert the threshold (batch_tokens <= threshold) is measured (the CPU cost grows with batch_tokens; the threshold is where CPU cost exceeds transfer cost) and not assumed — the "threshold is measured, not assumed" gate.
