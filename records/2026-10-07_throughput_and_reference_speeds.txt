MEASURED == above. TFLOP/s is 2*M*N*K / best-of-5 timing.
GB/s is the packed operand bytes (2 B/weight, f16) actually read per launch.

DEFECTS FOUND BY RUNNING, not by reading (both now fixed in the driver):
  D1. The first run died with "HIP ERROR unspecified launch failure" on the
      second case. Cause: dC was sized MMAX*NMAX with NMAX = 2*moe_inter =
      1536, but the down-projection has N = 2048. The kernel wrote past the
      allocation. Fixed: NMAX = hidden = 2048. A buffer sized from the wrong
      tensor shape fails as a crash, not as a wrong number, which is exactly
      why "the kernel compiled" is not evidence.
  D2. The driver called knj_guard_check()/knj_guard_code(), which do not
      exist. The ONLY guard in knj_wmma_guard.h is
      `int knj_wmma_guard(knj_wmma_dev *out)` returning 0 / 6 / 7. Fixed to
      the real API; the run now refuses correctly on the wrong arch.

DERIVED (measured per-launch x the model's GEMM count -- NOT end-to-end)
------------------------------------------------------------------------------
prefill 2048 tok, expert GEMM only      8269.0 us/layer   396.9 ms total
  -> expert-GEMM-only prefill ceiling     5159.8 tok/s
decode 1 tok, expert GEMM only           134.5 us/layer     6.5 ms total
  -> expert-GEMM-only decode ceiling       154.9 tok/s

READ THE DECODE ROW CAREFULLY. The M=1 and M=8 rows cost almost the SAME
(83 us vs 86 us). That is not noise and not an accident: at block tile BM=64
both shapes fall into a single block whose cooperative 64-row x K panel load
runs in full regardless of how many rows carry data. So the decode loss is
NOT "1/16 of the WMMA tile is useful" -- it is that the B (weight) panel is
streamed for a block that is 1/8 (M=8) or 1/64 (M=1) populated. The fix is
grouping across TOKENS, not a different instruction. The driver prints this
and the earlier "1x the grouped cost" line is the honest measurement of it.

19.12 TFLOP/s is 39% of the ~48.7 TFLOP/s dense-fp16 figure published for
the 9070 XT class (REFERENCE, zolotukhin.ai / JohnTDI). Headroom is expected
and stated as headroom, not as a result: larger BM/BN (128x128), LDS double
buffering, and dropping the bounds checks from the inner K loop are all
unimplemented, and the panel load loops here are unpipelined.

==============================================================================
4. WHAT THIS DOES AND DOES NOT ESTABLISH
==============================================================================
ESTABLISHED:
  - rocWMMA runs on gfx1201 and produces correct results (moe, attn, layout)
  - our tiled GEMM reaches 19.12 TFLOP/s at prefill shapes, 39% of class peak
  - the real target model's streaming bracket on this machine is 19.70..92.42
    t/s for tg, measured with the reference implementation
  - the hot-expert-residency prize is ~14-25x, from an independent PoC

NOT ESTABLISHED -- and the user's completion gate rests on these:
  - Kanjoos does NOT yet generate a single token end to end. There is no
    GGUF loader, no tokenizer, no sampling loop, no KV cache wired to real
    weights. Every rocWMMA result above is a KERNEL result against a host
    oracle. A kernel that is correct on synthetic operands has not been shown
    to be correct on real router-chosen expert rows from a real GGUF.
  - Therefore "inferences correctly", "is coherent", and "good prefill and
    token gen" are all still OPEN. They are not claimed here and must not be
    inferred from the kernel evidence above.
