# Worksheet — C16 Attention kernels

**What it owns:** the largest single device-time consumer in a decode step (the profile table in the reference example shows `attention` at 95% of device time).

**Why it exists (from `02-components.md` — C16 section; `01` §6; `09` §5; `00` §8.3):** two kernels (prefill + decode), structured from FA4/HipKittens translated to what RDNA actually has: two-tile ping-pong (two independent KV blocks in flight per workgroup, so one block's softmax overlaps the other's matmul),
selective rescaling (rescale the running max only when it actually changes, not every block — real VALU savings on a SIMT datapath), SGPR/VGPR split (address arithmetic and LDS copies issued from the scalar unit while the vector unit does the math). Prefill: tiled over Q blocks × KV blocks, GQA-aware head grouping, streaming softmax. Decode: single Q row per head — the whole point of the tiering work. Implementation split per arch: gfx1201 math = WMMA `f16`/`bf16`/`f8` via the `_gfx12` builtin + LDS tiles, with a SIMT fallback always compiled; gfx1031 math = `v_pk_fma_f16` + LDS tiles at 2 lanes/op (the only path, no WMMA). KV format: FP8 or FP16 on gfx1201, FP16 on gfx1031. No library to wrap — ROCm FlashAttention does not support RDNA4; this is written from scratch and validated against a CPU reference.

**The two kernels (verbatim `02-components.md` C16):**
* Prefill: tiled over Q blocks × KV blocks, GQA-aware head grouping, streaming softmax.
* Decode: single Q row per head, the whole point of the tiering work.

**The FA4/HipKittens structure translated to RDNA (verbatim `02-components.md` C16):**
* Two-tile ping-pong: two independent KV blocks in flight per workgroup, so one block's softmax overlaps the other's matmul.
* Selective rescaling: rescale the running max only when it actually changes, not every block. Real VALU savings on a SIMT datapath.
* SGPR/VGPR split: address arithmetic and LDS copies issued from the scalar unit while the vector unit does the math.

**Implementation split per arch (verbatim `02-components.md` C16):**

| | gfx1201 | gfx1031 |
|---|---|---|
| math | WMMA `f16`/`bf16`/`f8` via the `_gfx12` builtin + LDS tiles | `v_pk_fma_f16` + LDS tiles, 2 lanes/op |
| KV format | FP8 or FP16, dequant-to-FP16 in the prologue | FP16 |
| fallback | SIMT path, always compiled | the only path |

**Acceptance test (verbatim "done when"):**
* The decode kernel matches a CPU reference within tolerance for GQA, MQA and MLA at head_dim 64/128/192.
* Prefill throughput is within a stated fraction of the device's measured WMMA ceiling.

**Gates:**
* Depends on C14 (KV cache — the attention kernel reads paged KV from C14; the KV format (C15) is what the kernel's prologue dequantises (FP8→FP16 in the prologue on gfx1201); the KV must be VRAM-resident (C9's `ready()`) before the kernel runs — I4), C15 (KV codecs — the KV format is what C16's prologue dequantises; FP8 on gfx1201, FP16 on gfx1031; the dequant-to-FP16-in-the-prologue is what C15 provides on gfx1201; the codec is part of the cache key I5, so the kernel's KV format must match the cached page's codec), C9 (residency — the attention kernel asks C9's `ready()` for each KV block; if any is not ready, the planner has already failed over to the CPU path — never blocks; the attention path only ever sees VRAM-resident KV), C21 (telemetry — the "attention at 95% of device time" is a C21 number; the decode-kernel-matches-CPU-reference and prefill-throughput-within-fraction-of-WMMA-ceiling acceptance tests are C21 results), C22 (budget — the layer slab and KV budget come from C22's profile; C16's tiling granularity (Q blocks × KV blocks) is sized against the slab and the budget), C17 (expert GEMM — attention and expert GEMM are the two device-time consumers; the profile table distinguishes them; C16's attention device time is what C21 reports as `attention` device time; the attention kernel does not touch expert weights — those are C17's job).

**Coder notes / pitfalls:**
* The attention path only ever sees VRAM-resident KV (I4). A coder must not let the attention kernel read a KV page that is in RAM or NVMe — the page must have landed in VRAM before the layer arrives (the planner C9/C10/C11 guarantees this, or the CPU path is taken). The attention kernel asks C9's `ready()` for each KV block it needs; if any is not ready, the scheduler has already failed over (not the kernel stalling). A coder must not implement "attention kernel waits for KV page to arrive" — that is the synchronous-NVMe-read-on-the-critical-path failure (same as C14's I4).
* Two kernels, not one. Prefill and decode have different shapes (prefill: tiled over Q blocks × KV blocks, GQA-aware, streaming softmax — bulk; decode: single Q row per head — the whole point of the tiering work). A coder must implement both, with the right shape for each, and must not implement decode as a special case of prefill (decode is single-Q-row-per-head; prefill is tiled Q blocks × KV blocks). The profile table distinguishes them (attention is one column, but a coder should be able to break it into prefill/decode if the profiler supports it — the "attention at 95% of device time" is decode in the reference example, because decode is the steady-state).
* Two-tile ping-pong is the overlap mechanism. A coder must implement two independent KV blocks in flight per workgroup, so one block's softmax overlaps the other's matmul. This is the overlap that hides the KV-read latency inside the attention kernel (the KV is VRAM-resident, so the read is from VRAM at 589–598 GB/s — `00` §8.1 — not PCIe; but even VRAM reads have latency, and the ping-pong overlaps the softmax of one block with the matmul of the other). A coder must not implement a single-KV-block-per-workgroup decode that serialises softmax and matmul — that is the "no overlap inside the kernel" failure, and it wastes the VRAM-resident-KV latency advantage.
* Selective rescaling is a real VALU saving. A coder must implement "rescale the running max only when it actually changes, not every block" — this is not a micro-optimisation to skip; on a SIMT datapath, a VALU rescale every block is real work, and rescaling only on a max change is a real saving. A coder must not rescale every block "to be safe" — that throws away the saving.
* SGPR/VGPR split. A coder must issue address arithmetic and LDS copies from the scalar unit (SGPR) while the vector unit (VGPR) does the math. A coder must not do address arithmetic in VGPRs or LDS copies in VGPR-issued instructions — that is the "no SGPR/VGPR split" failure, and it wastes VGPRs and issue slots.
* WMMA on gfx1201: the `_gfx12` builtin + LDS tiles, with a SIMT fallback always compiled. A coder must implement the WMMA path via the `_gfx12` builtin (not the gfx11 `_w32` spelling — that is refused on gfx1201, `00` §1.1), and must keep the SIMT path compiled in as the fallback (so a future card without WMMA degrades, not fails; and so the WMMA path can be A/B'd against the SIMT path for the P1-3 numerics question — `00` §7.4a, the blocking unknown: the `_gfx12` A/B operand layout is not 8 consecutive f16, so a tiled expert GEMM written on that assumption reads wrong elements — the same caution applies to the attention WMMA path: do not assume the WMMA operand layout; verify it). A coder must not use the gfx11 `_w32` spelling on gfx1201 (it is refused) and must not assume 8-consecutive-f16 A/B layout (it is wrong — `00` §7.4a).
* gfx1031: `v_pk_fma_f16` + LDS tiles at 2 lanes/op, the only path (no WMMA — RDNA2 has no matrix units, `00` §1.4). A coder must not use WMMA on gfx1031. The gfx1031 attention path is SIMT-only (`v_pk_fma_f16` + LDS tiles), and the "2 lanes/op" is the RDNA2 fp16 throughput basis (`01` §7). A coder must not assume gfx1031 has WMMA or FP8.
* KV format per arch: FP8 or FP16 on gfx1201 (dequant-to-FP16 in the prologue), FP16 on gfx1031. A coder must implement the prologue dequant (FP8→FP16) on gfx1201 when the KV page is FP8 (C15's default), and must not dequant on gfx1031 (FP16 pages, no FP8). A coder must not read an FP8 page as FP16 without the dequant (that is the "a page written as FP8 is never read as BF16" invariant — I5 — and the dequant is the "online+fused" discipline from C15, applied to the attention prologue).
* No library to wrap — ROCm FlashAttention does not support RDNA4. A coder must write the attention kernels from scratch (translating the FA4/HipKittens structure to RDNA), and validate against a CPU reference. A coder must not try to wrap ROCm's FlashAttention (it does not support RDNA4 — that is the stated fact). A coder must not assume a library exists for RDNA4 attention.
* Validated against a CPU reference. A coder must validate the decode kernel against a CPU reference within tolerance for GQA, MQA, and MLA at head_dim 64/128/192 (`02-components.md` C16 done-when). This is the correctness standard for the attention kernel — not a full-output sweep against a double oracle (that is the expert GEMM/C17 discipline), but a CPU-reference-within-tolerance for the attention kernel across the config dimensions (GQA/MQA/MLA × head_dim 64/128/192). A coder must not ship an attention kernel without this validation, and must not validate only on FP16/GQA/head_dim-128 and assume the rest.

**Worked micro-example (host, sanity-check before device):**
Implement a fake C16 with a decode kernel (single Q row per head, two-tile ping-pong, selective rescaling, SGPR/VGPR split, VRAM-resident KV only, dequant-to-FP16 in the prologue if FP8) and a prefill kernel (tiled Q blocks × KV blocks, GQA-aware, streaming softmax), both validated against a CPU reference. Then: (1) implement the decode kernel with two-tile ping-pong (two independent KV blocks in flight per workgroup, one block's softmax overlaps the other's matmul) and assert the overlap is real (the kernel's VALU time for one block overlaps the LDS/read time for the other) — the two-tile-ping-pong gate; (2) implement selective rescaling (rescale the running max only when it actually changes, not every block) and assert the rescale operations are fewer than the number of blocks (only on max change) — the selective-rescaling gate; (3) implement the SGPR/VGPR split (address arithmetic and LDS copies from the scalar unit; math from the vector unit) and assert address/ LDS work is on SGPRs and math is on VGPRs — the SGPR/VGPR-split gate; (4) implement the "attention kernel reads only VRAM-resident KV" rule (asks C9's `ready()` for each KV block; if any not ready, the planner has already failed over to CPU — never waits on a RAM/NVMe block) and assert the kernel never blocks on a KV page — the I4 gate; (5) implement the prologue dequant (FP8→FP16) on gfx1201 when the KV page is FP8, and assert no dequant on gfx1031 (FP16 pages, no FP8) and no reading an FP8 page as FP16 without the dequant (I5) — the KV-format-per-arch + online-fused-prologue gate; (6) implement BOTH kernels (prefill: tiled Q blocks × KV blocks, GQA-aware, streaming softmax; decode: single Q row per head) and assert they are distinct shapes, not decode-as-a-special-case-of-prefill — the two-kernels gate; (7) implement the gfx1201 WMMA path via the `_gfx12` builtin (not the gfx11 `_w32` spelling — refused on gfx1201) + LDS tiles, AND keep the SIMT path always compiled in as fallback, and assert the SIMT fallback is reachable (e.g. on a fake card without WMMA, or as the P1-3 A/B basis) — the WMMA-via-_gfx12-with-SIMT-fallback gate; (8) assert gfx1031 uses `v_pk_fma_f16` + LDS tiles at 2 lanes/op, the only path (no WMMA — RDNA2 has no matrix units) — the gfx1031-SIMT-only gate; (9) validate the decode kernel against a CPU reference within tolerance for GQA, MQA, and MLA at head_dim 64/128/192, and assert the validation covers all those dimensions (not just FP16/GQA/head_dim-128) — the CPU-reference-validation gate; (10) assert the KV format the kernel reads matches the cached page's codec (I5 — the codec is part of the cache key) — the KV-format-matches-cached-page-codec gate.
