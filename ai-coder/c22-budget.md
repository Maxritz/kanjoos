# Worksheet — C22 Memory budget manager

**What it owns:** turning detected hardware into the policy numbers.

**Why it exists (from `02-components.md` — C22 section; `04` §2/§3; `01` §3):** the VRAM×RAM profile matrix (VRAM ∈ {6, 8, 12, 16} GiB × RAM ∈ {16, 24, 32, 48, 64, 96} GiB) is the starting point for every policy number: VRAM ceiling, KV block size, layer slab, lookahead tokens, H2D in flight, prefetch extent, expert slots, WARM KV target, pinned pool cap.
Values are **starting points overridden by measurement** (C3 autotuner rewrites block size, slab depth, prefetch depth, transfer extent from observed bandwidth and hit rate — never constants). The `kanjoos.toml` is a starting point, not a decision.

**Spec lines that must hold:**
* `02-components.md` — C22 section (verbatim: the Profile struct and `select()` API, the VRAM×RAM matrix rows, the values-are-starting-points-overridden-by-measurement rule, the `kanjoos.toml` as starting point, the done-when).
* `04-memory-tiering.md` §2 (VRAM profiles — the VRAM ceiling, KV block, layer slab, lookahead tokens, H2D in flight, prefetch extent, expert slots per VRAM class: 6 GiB → 5.25 GiB ceiling, 16 block, 2 slab, 32–128 lookahead, 2–4 H2D, 2–8 MiB prefetch, small fixed pool; 8 GiB → 7.00 GiB, 32, 4, 64–192, 4–6, 4–16 MiB, measured; 12 GiB → 10.50 GiB, 32, 4, 64–256, 4–8, 4–16 MiB, measured; 16 GiB → 14.00 GiB, 32, 4, 128–512, 8–16, 8–32 MiB, largest that fits.) and §3 (RAM profiles — WARM_KV_LIMIT = min(0.65 × phys_ram, phys_ram − 8 GiB); PINNED_POOL = 2 GiB (24/32), 3 GiB (48), 6 GiB (96); the table; the 96 GiB case where W4 experts (14.13 GiB) fit entirely warm and W6 (20.7 GiB) fits with room to spare — the configuration where the engine is genuinely excellent).
* `01-architecture.md` §3.1 (VRAM: VRAM_CEILING = profile_ceiling(detected_vram); MODEL_DEVICE = resident weights; WORKSPACE = activations, LDS double-buffering, expert staging, logits; HOT_KV = VRAM_CEILING − MODEL_DEVICE − WORKSPACE − SAFETY; EXPERT_SLOTS = f(HOT_KV). The reserve is measured at startup (allocate and free a set of buffers at the sizes the engine will actually use, take the high-water mark). VRAM_USABLE = what `hipMemGetInfo` reports after that; the engine refuses to start if under 3.5 GiB.) and §3.2 (RAM: WARM_KV_LIMIT, WARM_EXPERT, PINNED_POOL; dynamic shrink order: PINNED > active request's KV > active request's experts > WARM > COLD; dynamic shrink is mandatory, not optional.)
* `01-architecture.md` §4 (the transfer budget — the number the whole plan is sized against: at W4, 0.95 GB of expert weight per generated token if zero reuse; against ~4 GB/s NVMe → ~4.3 tok/s; against ~20 GB/s PCIe pinned H2D (ASSUMPTION, P0-1) → ~21 tok/s; VRAM-resident slot → 0 bytes, unbounded by I/O. The W4 expert bank = 14.13 GiB (corrected from 13.8 — `gemm_w4.hip`'s 0.5234 B/weight, not 0.5). The cold-start budget vs steady-state budget distinction (the 0.95 GB/token is cold-start; steady-state is 948 MB experts + 474 MB attention + 163 MB lm_head = 1,586 MB/token — `00` §9.3 / `kv_roofline.py` section C). The KV side is the one that gets worse with use (KV overtakes expert weight traffic at ~9.6 K tokens FP16 — `00` §9.3 / `kv_roofline.py` section D).)

**Interface (verbatim `02-components.md` C22):**
```cpp
struct Profile { uint64_t vram_ceiling; uint32_t token_block, layer_slab,
                 size_t prefetch_bytes; size_t expert_slots; size_t warm_kv;
                 uint32_t lookahead_tokens; int h2d_inflight; };
Profile select();  // from (VRAM class x RAM class) and measured bandwidth
```

**The `kanjoos.toml` (verbatim `02-components.md` C22):**
```toml
# kanjoos.toml — a starting point, not a decision
[gpu]
vram_class = "auto"          # 6 | 8 | 12 | 16
vram_ceiling_gib = 0         # 0 = measured
token_block = 32
layer_slab = 4
prefetch_mib = 8

[ram]
warm_fraction = 0.65
min_free_gib = 8
pinned_pool_gib = 3

[nvme]
cache_fraction = 0.35
max_cache_tib = 2

[profile]
profiling = "off"            # off | counters | full | table
```

**Acceptance test (verbatim "done when"):**
* A run on each VRAM class reports the profile it selected and the measurement that justified it.
* Overriding any value in the file visibly changes the run.

**Gates:**
* Depends on C2 (DeviceCaps — the detected VRAM, ReBAR state, arch; C22's `select()` reads C2's detected hardware to pick the VRAM class and the RAM class, and to measure VRAM_USABLE and the reserve), C3 (autotuner — C22's policy numbers (block size, slab depth, prefetch depth, transfer extent) are starting points overridden by C3's measurement; C22's `select()` gives the starting points, C3 rewrites the tunable ones from observed bandwidth and hit rate; C22 must be able to report both the starting point and the C3-overridden value), C4 (loader — C22's VRAM ceiling and workspace budget are what C4's resident buffers must fit within; C22's SAFETY (measured high-water mark of the runtime's own allocations) is what C4's load must leave room for), C7 (host tier — C22's WARM_KV_LIMIT, warm experts, and pinned pool cap are what C7 uses; C22 sets these from the RAM class and the profile), C8 (slot allocator — C22's expert_slots is what C8's slot pool is sized to; C22's VRAM ceiling and the KV/expert split are what determine C8's slot count), C9/C10/C11/C12/C13/C14/C15 (the KV/cache/transfer/residency/codecs — C22's KV block, layer slab, prefetch extent, lookahead tokens, H2D in flight are what these components use; C22 sets these from the VRAM class and the profile), C21 (telemetry — the "run on each VRAM class reports the profile it selected and the measurement that justified it" acceptance is a C21 result; the "overriding any value visibly changes the run" acceptance is a C21 result; C22's reported profile and measurements are C21 columns), C24 (platform — the detected hardware (VRAM class, RAM class, ReBAR state) comes from C24's doctor; C22's `select()` reads C24's resolved platform facts; the pinned pool cap (Windows `VirtualLock` / Linux `mlock` + RLIMIT) is C24's mechanism, C22's cap is the policy).

**Coder notes / pitfalls:**
* Values are starting points, not decisions. A coder must implement `select()` to return starting points from the VRAM×RAM matrix (and the `kanjoos.toml` overrides), and must implement the C3 autotuner to override the tunable ones (block size, slab depth, prefetch depth, transfer extent) from observed bandwidth and hit rate. A coder must not treat the matrix values as final — they are the starting point; C3's measurement is what makes them final. A coder must report both the starting point and the C3-overridden value (C21) — the acceptance test ("reports the profile it selected and the measurement that justified it") requires both.
* The VRAM ceiling is measured, not assumed. A coder must implement the reserve measurement (`01` §3.1: allocate and free a set of buffers at the sizes the engine will actually use, take the high-water mark) and the `hipMemGetInfo` after-that check, and must refuse to start if VRAM_USABLE < 3.5 GiB. A coder must not assume the VRAM ceiling from the card's advertised VRAM — the reserve is measured, and VRAM_USABLE is what is left after the reserve and the runtime's own allocations. A coder must not start on a card where VRAM_USABLE < 3.5 GiB — that is the refuse-to-start gate.
* The SAFETY term (measured high-water mark of the runtime's own allocations) is what makes the VRAM allocation split real. A coder must measure SAFETY (the runtime's own allocations — the op graph, the event ring, the profiler buffers, the C21 accumulators, etc.) and include it in the split (VRAM_CEILING − MODEL_DEVICE − WORKSPACE − SAFETY = HOT_KV + EXPERT_SLOTS). A coder must not omit SAFETY or assume a constant — it is measured, and it is the term that keeps the split honest (without it, the split over-promises HOT_KV + EXPERT_SLOTS).
* The KV/expert split is the most consequential policy in the engine (`04` §2: "More VRAM to KV → longer context, but more cold experts per token. More VRAM to expert slots → higher hit rate, but less context."). A coder must implement the split as a policy (default split per profile: 6 GiB → 35% KV / 65% experts; 8 GiB → 45/55; 12 GiB → 50/50; 16 GiB → 45/55, biased back toward experts when the model's active set is bandwidth-bound — detected at runtime from the C21 profile, not guessed), and must let the user pin either side. A coder must report the consequence in tokens/s and context length, not hide it. A coder must not hardcode the split — it is a policy, set by the profile and optionally pinned by the user, and it is the thing that trades context for hit rate (the thing the whole engine is about).
* The 6 GiB case is a workload, not a failure (`04` §2.1). A coder must implement the 6 GiB profile honestly — at 5.25 GiB with a 30B-class MoE, the model itself may not fit, and the engine must say which of (smaller model, full RAM residency with a large warm tier, or a heavily expert-compressed build (C5 mixed precision) where the expert bank fits W4/W6 and the trunk is small) it is doing and what it costs. The residency label (VRAM-resident / RAM-resident / storage-assisted / storage-bound — `04` §7) is what C21 reports. A coder must not pretend a 6 GiB card can do a 30B MoE resident — it cannot at W4 (the expert bank is 14.13 GiB — `kv_roofline.py` section K), and at W3 (operating point, 11.79 GiB resident — `ai-coder/operating-point.md`) the KV budget is 3.46 GiB, which on a 6 GiB card (5.25 GiB ceiling) leaves room for KV but the expert bank (11.79 GiB) does not fit in 5.25 GiB VRAM — so the 6 GiB card cannot run a 30B MoE resident at all; it would be RAM-resident or storage-bound, and the engine must say so. A coder must not claim a 6 GiB card can do a 30B MoE resident — that is the honesty requirement.
* The 96 GiB host is where the engine is genuinely excellent (`04` §3). A coder must implement the 96 GiB profile honestly — at 96 GiB host, W4 experts (14.13 GiB) fit entirely warm, and W6 (20.7 GiB) fits with room to spare. So the 96 GiB host with a 12–16 GiB card running a 30B-class MoE at usable speed is the design target (`04` §3: "the design target is a 96 GiB host with a 12–16 GiB card running a 30B-class MoE at usable speed, not a 6 GiB card doing the impossible."). A coder must not treat the 96 GiB case as exotic — it is the target. A coder must implement the WARM_EXPERT for 96 GiB (the warm experts typical is ~70 GiB — `04` §3 table) and the pinned pool cap (6 GiB for 96 GiB) and the WARM_KV_LIMIT (62.4 GiB for 96 GiB) as the starting points, and let C3 measure them.
* The `kanjoos.toml` is a starting point, not a decision. A coder must implement the toml as a starting-point configuration (the values in it are the matrix defaults, overridable), and must implement the "overriding any value visibly changes the run" acceptance (a user override of, e.g., `token_block` or `layer_slab` or `pinned_pool_gib` must visibly change the run — the C21 profile must show the changed value and its effect). A coder must not treat the toml as a hard configuration that the engine ignores — every value in it must be wired to a component (C7, C8, C10, C11, C14, etc.) and must visibly affect the run when overridden.

**Worked micro-example (host, sanity-check before device):**
Implement a fake C22 with the VRAM×RAM matrix (6/8/12/16 GiB × 16/24/32/48/64/96 GiB), the `select()` API (from detected VRAM class and RAM class and measured bandwidth), the `Profile` struct, the `kanjoos.toml` as starting point, and the C3 autotuner override (block size, slab depth, prefetch depth, transfer extent from observed bandwidth and hit rate). Then: (1) implement `select()`: given a detected VRAM class and RAM class (from C24's doctor) and the `kanjoos.toml` overrides, return the starting-point Profile from the matrix (VRAM ceiling, token_block, layer_slab, prefetch_bytes, expert_slots, warm_kv, lookahead_tokens, h2d_inflight) — and assert the VRAM ceiling matches the matrix (6 GiB→5.25, 8→7.00, 12→10.50, 16→14.00) and the RAM-derived values match the matrix (WARM_KV_LIMIT = min(0.65×phys_ram, phys_ram−8 GiB); PINNED_POOL = 2 GiB (24/32), 3 GiB (48), 6 GiB (96)) — the "VRAM×RAM matrix starting points" gate; (2) implement the reserve measurement and VRAM_USABLE check: allocate and free a set of buffers at the sizes the engine will actually use, take the high-water mark as SAFETY, compute VRAM_USABLE = `hipMemGetInfo` after that, and assert the engine refuses to start if VRAM_USABLE < 3.5 GiB — the "VRAM_USABLE measured, refuse if < 3.5 GiB" gate; (3) implement the VRAM allocation split: VRAM_CEILING − MODEL_DEVICE − WORKSPACE − SAFETY = HOT_KV + EXPERT_SLOTS, with MODEL_DEVICE = resident weights (trunk + attention + router + head), WORKSPACE = activations, LDS double-buffering, expert staging, logits — and assert the split is real (HOT_KV + EXPERT_SLOTS = what is left after the reserve and SAFETY) — the "VRAM split with SAFETY" gate; (4) implement the KV/expert split policy: default split per profile (6 GiB→35/65, 8 GiB→45/55, 12 GiB→50/50, 16 GiB→45/55, biased toward experts when bandwidth-bound detected from C21 profile) and the user-pin option (user can pin either side) — and assert the consequence is reported in tokens/s and context length (C21) — the "KV/expert split is policy, reported, not hidden" gate; (5) implement C3 autotuner override: C3 rewrites block size, slab depth, prefetch depth, transfer extent from observed bandwidth and hit rate, and C22 reports both the starting point and the C3-overridden value (C21) — and assert overriding a value in `kanjoos.toml` visibly changes the run (C21 shows the changed value and its effect) — the "starting point overridden by measurement, override visibly changes run" gate; (6) implement the 6 GiB case honestly: at 5.25 GiB ceiling with a 30B MoE (W4 expert bank 14.13 GiB, W3 operating point 11.79 GiB resident) the model does not fit resident, and the engine reports the residency label (RAM-resident or storage-bound) and says what it is doing and what it costs (smaller model, full RAM residency with large warm tier, or C5 mixed-precision build where expert bank fits W4/W6 and trunk is small) — the "6 GiB is a workload, not a failure; report residency label honestly" gate; (7) implement the 96 GiB host case honestly: W4 experts (14.13 GiB) fit entirely warm, W6 (20.7 GiB) fits with room to spare; WARM_EXPERT for 96 GiB is ~70 GiB, PINNED_POOL 6 GiB, WARM_KV_LIMIT 62.4 GiB — and assert these are the starting points (overridable by C3) — the "96 GiB host is the target; implement honestly" gate.
