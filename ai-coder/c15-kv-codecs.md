# Worksheet — C15 KV codecs

**What it owns:** how KV bytes are represented in each tier.

**Why it exists (from `02-components.md` — C15 section; `01` §7; `09` §5):** the KV codec is a per-tier, per-arch decision, and it is part of the cache key (I5). FP8 is the default **because of the hardware** — gfx1201 has a native FP8
  path at 2× FP16 throughput and rocWMMA supports `f8/f32/f32` there; gfx1031 has no FP8 at all, so proposing FP8 KV there would be proposing a kernel that does not exist. FP16/BF16 is the gfx1031 default. TurboQuant 4bit-nc is an opt-in second tier
  behind a quality gate (the vLLM study found it 2.3–3.7× capacity at 40–52% throughput cost vs BF16, useful only when KV is the binding constraint; 3-bit variants are rejected by that study on accuracy and are not offered). Quantisation is online and fused into the
  KV write — a KV page is written already in its storage representation, so there is no separate quantise pass on the miss path (I2). The codec is part of the cache key — a page written as FP8 is never read as BF16.

  codec is part of the cache key; done-when).
* `01-architecture.md` §7 (what is different between the two targets: gfx1201 has native FP8, 2× FP16; gfx1031 has no FP8; KV codec default: FP8 E4M3 on gfx1201, FP16/BF16 on gfx1031).
* `09-kv-engine-architecture.md` §5 (I2: no dequantisation on the miss path — the bytes that move are the bytes the GEMM/KV consumes; `NVMe → RAM → VRAM → use` in a kernel-native format. I5: the codec is part of the cache key. A KV page written as FP8 is never read as BF16.)
* `00-verified-facts.md` §1.1 (gfx1201 has native FP8 via WMMA `f8/f32/f32` — the hardware basis for the FP8-KV-on-gfx1201 default).

**The tier×arch table (verbatim `02-components.md` C15):**

| tier | gfx1201 | gfx1031 |
|---|---|---|
| VRAM | FP8 E4M3 (native WMMA f8) | FP16/BF16 |
| RAM | same | same |
| NVMe | FP8, or TurboQuant 4bit-nc when admitted | FP16 |

**Acceptance test (verbatim "done when"):**
* FP8 KV matches BF16 KV within the configured tolerance on deterministic prompts.
* The codec round-trips through the NVMe tier without drift.

**Gates:**
* Depends on C14 (KV cache — C15's codec is what C14's KV pages are stored in; C14's block format is what C15 provides; the codec is part of C14's block key), C13 (radix index — C15's codec is part of the cache key I5; a page written in one codec is not a hit for a request expecting another),
  C11 (transfer — C15's codec is what C11 moves (the bytes that move are the KV page in its storage representation — no dequantise staging on the miss path, I2); C15's online+fused quantisation is what C11's NVMe write stores),
  C21 (telemetry — the "FP8 KV matches BF16 within tolerance" acceptance is a C21 result; the "codec round-trips through NVMe without drift" is a C21 result; the TurboQuant quality gate's pass/fail is a C21/quality result),
  C22 (budget — C15's codec choice is what drives the KV budget (the KV bytes/token is `sizeof(codec)` in `09` §9.2); C22's KV budget depends on the codec; a coarser codec (FP8, TurboQuant 4bit-nc) changes the KV budget and thus the Class A ceiling and the Class B price).

**Coder notes / pitfalls:**
* FP8 is the default on gfx1201 **because of the hardware** (native FP8 via WMMA `f8/f32/f32`, 2× FP16 throughput — `00` §1.1, `01` §7). A coder must not make FP8 a default on gfx1031 (it has no FP8 — proposing FP8 KV there is proposing a kernel that does not exist). A coder must not make FP8 a "free" default — it is the default because the hardware supports it and it halves the KV bytes/token (98,304 → 49,152 B/token — `kv_roofline.py` section B), which is a real capacity win (it doubles the Class A context at a given KV budget, and halves the Class B price). The default is justified by the hardware and the capacity win, not by assumption.
* TurboQuant 4bit-nc is opt-in behind a quality gate, not a default. A coder must not ship TurboQuant 4bit-nc as a default. The vLLM study figures (2.3–3.7× capacity at 40–52% throughput cost vs BF16) are the basis for "useful only when KV is the binding constraint" — i.e. when the Class B price or the KV budget is the bottleneck, not the compute. A coder must gate TurboQuant 4bit-nc behind a quality gate (the KV output must match BF16 within tolerance on deterministic prompts, or it is not admitted), and must not offer 3-bit variants (rejected by the vLLM study on accuracy). A coder must not assume TurboQuant is smaller than it is — the BITCOS correction (`02-components.md` C5, `08` Phase 7) is the lesson: measure size **and** kernel cost per tensor, and do not assume a codec is smaller once scales are counted (BITCOS is ~3% larger than five-trit for CAT-Q Qwen3-30B-A3B once scales are counted — the same caution applies to any "this codec is smaller" claim).
* Online+fused quantisation into the KV write (I2). A coder must not implement a separate quantise pass on the miss path. A KV page is written already in its storage representation (FP8, or TurboQuant 4bit-nc if admitted), so the bytes that move (C11) are the bytes that are stored and read — no dequantise-to-BF16 staging. This is the I2 invariant (no dequantisation on the miss path). A coder must not write a KV page in BF16 and quantise it on read — that is the dequantise-on-the-miss-path failure (it costs the quantise on every miss, and the bytes that move are not the bytes that are stored).
* The codec is part of the cache key (I5). A coder must include the KV codec in the block's cache key (model fingerprint + arch + dtype + layout + RoPE config + tokenizer + attention implementation version + KV codec + impl-version). A page written as FP8 is never a hit for a request expecting BF16, and vice versa. A coder must not read a page written in one codec as another codec — that is the "a cache page from a different build is not readable" invariant, and the codec is part of what makes builds different.
* FP8 matches BF16 within tolerance (the acceptance test). A coder must measure FP8 KV against BF16 KV on deterministic prompts and report the tolerance (C21). A coder must not assert bit-identity for FP8 vs BF16 (it is a lossy codec relative to BF16 — it is a declared precision reduction, priced and recorded per page, not a tier move; I7/`00` §9.7). The "within tolerance" is the standard, and the tolerance is a configured, measured number, not an assumed one. A coder must not ship FP8 without measuring it against BF16 on deterministic prompts — the acceptance test is the gate.
* The codec round-trips through NVMe without drift (the acceptance test). A coder must measure a KV page written in the storage codec, persisted to NVMe (C11/C12), reloaded, and read, and assert it matches the original within tolerance (C21). A coder must not assume NVMe persistence preserves the codec's precision — bit rot, partial writes, and codec drift are real; the round-trip test is the gate. (This is the same discipline as C6's checksum-on-read and corrupt-object handling — the round-trip test is the KV-codec version of that.)
* The codec choice drives the KV budget (C22). A coder must recompute the KV budget (and thus the Class A ceiling and the Class B price) when the codec changes, because the KV bytes/token is `sizeof(codec)` (`kv_roofline.py` section B: FP16 98,304, FP8 49,152, INT8 g128 50,304, INT4 g128 25,728 — each includes the 3 B/group metadata). A coarser codec doubles the Class A context at a given KV budget and halves the Class B price. A coder must not treat the codec as a free quality knob — it is a capacity knob (it changes the KV budget, the Class A ceiling, and the Class B price), and the operating point (W3 g128, 37.8 K FP16 / 75.6 K FP8 context at 16 GiB — `ai-coder/operating-point.md`) is sized against the codec. A coder must not change the codec without re-deriving the KV budget and the Class A/B numbers (via `kv_roofline.py`).

**Worked micro-example (host, sanity-check before device):**
Implement a fake C15 with the tier×arch table (FP8 E4M3 on gfx1201 VRAM/RAM/NVMe; FP16/BF16 on gfx1031; TurboQuant 4bit-nc on gfx1201 NVMe only when admitted), online+fused quantisation into the KV write (I2), the codec as part of the cache key (I5), and the two acceptance tests. Then: (1) implement FP8 KV on gfx1201 and assert it matches BF16 KV within the configured tolerance on deterministic prompts (C21) — the FP8-vs-BF16-tolerance gate; assert bit-identity is NOT asserted for FP8 vs BF16 (it is a lossy codec relative to BF16 — a declared precision reduction, priced and recorded per page, not a tier move — I7/`00` §9.7) — the "no bit-identity claim for FP8 vs BF16" gate; (2) implement the codec as part of the cache key and assert a page written as FP8 is never a hit for a request expecting BF16, and is never read as BF16 (I5) — the codec-is-part-of-key gate; (3) implement TurboQuant 4bit-nc as opt-in behind a quality gate (the KV output must match BF16 within tolerance on deterministic prompts to be admitted) and assert it is not a default, and that 3-bit variants are not offered (rejected by the vLLM study on accuracy) — the TurboQuant-behind-a-gate gate; (4) implement online+fused quantisation into the KV write (a KV page is written already in its storage representation — FP8 or TurboQuant 4bit-nc — so the bytes that move are the bytes that are stored and read, no dequantise-to-BF16 staging on the miss path, I2) and assert there is no separate quantise pass on the miss path — the I2-no-dequantise-on-miss-path gate; (5) implement the NVMe round-trip test (write a KV page in the storage codec, persist to NVMe via C11/C12, reload, read, assert it matches the original within tolerance — C21) — the codec-round-trips-through-NVMe-without-drift gate; (6) implement the codec-choice-drives-KV-budget re-derivation: when the codec changes, recompute `bytes/token = 2 × layers × kv_heads × head_dim × sizeof(codec)` (from config + C15's codec), and re-derive the Class A ceiling and Class B price (via `kv_roofline.py`), and assert the numbers change as expected (FP8 halves KV bytes/token from 98,304 to 49,152 — `kv_roofline.py` section B; doubles Class A FP16 context from 37.8 K to 75.6 K at the W3 operating point — `ai-coder/operating-point.md`; halves the Class B price — `04` §6.1) — the codec-changes-KV-budget gate; (7) assert the gfx1201 default (FP8) is justified by the hardware (native FP8 via WMMA `f8/f32/f32`, 2× FP16 throughput — `00` §1.1, `01` §7) and by the capacity win (halves KV bytes/token), not by assumption — the FP8-default-justified gate; and assert FP8 is NOT the default on gfx1031 (no FP8 hardware) — the gfx1031-no-FP8 gate.
