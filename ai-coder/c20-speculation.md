# Worksheet — C20 Speculative decoding

**What it owns:** converting leftover bandwidth into tokens.

**Why it exists (from `02-components.md` — C20 section; `01` §1 (point 4: "spending every byte that frees up on either lower-bit KV cache or speculative decoding")):** speculation converts leftover bandwidth (and leftover expert-slot hit rate) into tokens/s, but only if it is lossless (I6: accepted output is bit-identical to non-speculative decoding under the same seed) and priced correctly (MTP first because it is free (the head is already resident and costs zero I/O), then one loader for DFlash/DFlash2/DSpark, then DSpark's confidence head wired into C10 so drafting stops early when the next verification pass would stall on cold experts anyway).

**Spec lines that must hold:**
* `02-components.md` — C20 section (verbatim: MTP first (the head is already resident and costs zero I/O); one DFlash / DFlash2 / DSpark loader with an arch compatibility check; DSpark's confidence head wired into C10 so drafting stops early when the next verification pass would stall on cold experts anyway; done-when).
* `01-architecture.md` §1 (point 4 — speculation is one of the four ways the engine wins; "spending every byte that frees up on either lower-bit KV cache or speculative decoding" — speculation is the "leftover bandwidth into tokens" lever; it is gated on measurement, and it is lossless (I6)).
* `01-architecture.md` §5 (I6 — speculation is lossless; accepted output is bit-identical to non-speculative decoding under the same seed. This is the correctness standard for speculation — the acceptance test ("bit-identical to non-speculative under a fixed seed") is the gate.)
* `08-roadmap.md` — Phase 5 exit gate (bit-identical to non-speculative under a fixed seed; MTP adds zero load-time H2D; `experts touched / accepted token` is reported and adapts draft width), Acceptance criteria (speculation is bit-identical to non-speculative under a fixed seed; deterministic sampling reproduces under a fixed seed, with and without speculation).
* `04-memory-tiering.md` §5 (the discipline — the attention path never issues a storage read; if a required page is not in VRAM when its layer arrives, the scheduler has already either found it in RAM and issued H2D early enough, found it in NVMe and issued the read early enough, or failed to and taken the CPU/expert fallback (C19) rather than stalling. Speculation's verification pass must obey this — the drafter's proposed tokens are verified by a real forward pass, and if the verification pass would stall on a cold expert, the confidence head (DSpark, wired into C10) stops drafting early, so the verification pass does not stall.)

**The three components (verbatim `02-components.md` C20):**
* MTP drafter (zero extra load I/O) — the head is already resident; MTP drafts tokens from the head's logits at no extra load I/O.
* One DFlash / DFlash2 / DSpark loader with an arch compatibility check — one loader for the drafter families, with an arch compatibility check (the drafter must run on the target arch; the loader checks and refuses a drafter the arch cannot run).
* DSpark's confidence head wired into C10 so drafting stops early when the next verification pass would stall on cold experts anyway — the confidence head predicts whether the next verification pass will stall (on cold experts), and if so, drafting stops early (no point drafting tokens that will be discarded when the verification pass stalls).

**Acceptance test (verbatim "done when"):**
* Bit-identical to non-speculative under a fixed seed.
* MTP adds zero load-time H2D.
* `experts touched / accepted token` is reported and adapts draft width.

**Gates:**
* Depends on C16 (attention — the drafter and the verifier both run attention; the drafter runs a forward pass (or a partial forward pass) to draft tokens; the verifier runs a forward pass to verify the drafted tokens; both use C16's attention kernels; the drafter's forward pass must obey the "attention path only sees VRAM-resident KV" rule (I4) — the drafter's KV must be VRAM-resident, or the planner has arranged it, or the drafter does not draft that token), C17 (expert GEMM — the drafter and verifier both run expert GEMMs; the drafter's expert GEMMs must obey the "group or die on load" and "no dequantise staging on the miss path (I2)" rules; the verifier's expert GEMMs are the real forward pass that verifies the drafted tokens; the `experts touched / accepted token` is a C17/C18/C21 number), C18 (router — the drafter and verifier both run the router (C18) to select experts; the drafter's router selection is what the drafter drafts; the verifier's router selection is what verifies the drafted tokens; the drafter's selection must be the model's router (I3) — the drafter is the model's router, not an approximation, unless the drafter is a learned drafter that is itself verified), C19 (fallback — the verifier's forward pass may hit cold experts; if so, the confidence head (DSpark, wired into C10) has already stopped drafting early, so the verifier does not stall; if a cold expert is hit anyway, C19 is the fallback (CPU compute or BAR read), not a stall), C10 (prefetch/predict — DSpark's confidence head is wired into C10; the confidence head predicts whether the next verification pass would stall on cold experts, and if so, drafting stops early; the `experts touched / accepted token` is a C10/C17/C18/C21 number), C14/C15/C13/C11/C9 (the KV/cache/transfer/residency for the drafter's and verifier's forward passes — the drafter's KV must be VRAM-resident (C9's `ready()`), the drafter's KV codec (C15) must match the cached page's codec (I5), the drafter's KV blocks are the paged KV (C14) mapped by the radix index (C13), and the drafter's KV reads are moved by C11 (async, VRAM-resident only)), C21 (telemetry — `experts touched / accepted token` is a C21 number; the bit-identical-to-non-speculative acceptance is a C21 result; the MTP-zero-load-time-H2D acceptance is a C21 result; the draft-width-adapts-to-cold-experts acceptance is a C21 result), C22 (budget — the draft width is bounded by the VRAM/KV/expert budget (C22) — drafting more tokens uses more KV and more expert slots; the confidence head stops drafting early when the next verification pass would stall on cold experts, which is the budget/horizon-aware behavior), C24 (platform/arch — the drafter loader's arch compatibility check is C24).

**Coder notes / pitfalls:**
* MTP first, because it is free (the head is already resident and costs zero I/O). A coder must implement MTP (multi-token prediction from the head) as the first drafter, because the head is already resident (the LM head is resident in VRAM — `01` §4: the lm_head is 163 MB/token read every step, and it is resident — it is part of MODEL_DEVICE in the VRAM allocation split, `01` §3.1). So MTP drafts tokens from the head's logits at no extra load I/O (no expert weights to load, no KV to load beyond what the verifier already loads). A coder must not treat MTP as requiring extra I/O — it is the free drafter, because the head is resident. (The head is read every step anyway — `01` §4.1: the lm_head is 163 MB/token, read every step, can't be amortised by routing or batching because every token needs its own logits. So MTP, which reuses the head's logits for the next few tokens, is free relative to the no-speculation baseline — the head is being read anyway.)
* One loader for DFlash / DFlash2 / DSpark, with an arch compatibility check. A coder must implement one loader that can load the three drafter families (DFlash, DFlash2, DSpark), with an arch compatibility check (the drafter must run on the target arch — gfx1201 or gfx1031; the loader checks the drafter's arch requirements against the target arch's caps (C2's DeviceCaps) and refuses a drafter the arch cannot run). A coder must not ship a drafter the target arch cannot run (e.g. a WMMA-based drafter on gfx1031 — gfx1031 has no WMMA, `00` §1.4; the loader's arch compatibility check must refuse it).
* DSpark's confidence head wired into C10, so drafting stops early when the next verification pass would stall on cold experts. A coder must implement DSpark's confidence head (a learned head that predicts whether the next verification pass would stall on cold experts) and wire it into C10 (the prefetch/predict component) so that drafting stops early when the confidence head predicts a stall. The point: if the verifier's next forward pass would stall on a cold expert (the expert is not resident and will not arrive in time — C9's `ready()` is false and the planner has determined it will not arrive in time, so C19 would be the fallback, which is slower than not drafting the token), then drafting that token is wasted (the drafted token will be discarded when the verifier stalls or falls back), so the confidence head stops drafting early. A coder must wire the confidence head into C10 so the drafting loop consults the confidence head and stops early when the confidence head predicts a stall. A coder must not draft tokens regardless of cold-expert risk — that is the "drafting stops early when the next verification pass would stall on cold experts anyway" rule, and it is the budget/horizon-aware behavior that makes speculation not waste bandwidth on tokens that will be discarded.
* Bit-identical to non-speculative under a fixed seed (I6). A coder must implement speculation so that, under a fixed seed, the accepted output (the tokens that survive verification) is bit-identical to the non-speculative output (the tokens the non-speculative forward pass would have produced). A coder must not implement speculation that changes the output (e.g. a drafter that changes the routing, or a verifier that accepts a drafted token that the non-speculative pass would not have produced) — that violates I6. The acceptance test (bit-identical under a fixed seed) is the gate. A coder must not claim a speculation win without this test — a speculation that changes the output is wrong, not "almost the same".
* MTP adds zero load-time H2D. A coder must implement MTP so it adds zero load-time H2D — the head is resident, so MTP's drafts come from the head's logits with no extra H2D. A coder must not have MTP trigger an H2D (e.g. if MTP's draft causes a KV block to be loaded, that H2D is part of the normal planner (C9/C10/C11) work, not an MTP-specific H2D; but MTP itself — the head's logits — adds no H2D). A coder must not claim "MTP adds zero load-time H2D" if MTP triggers an H2D that the no-speculation baseline would not have — that would be an MTP-specific H2D, which violates the "zero load-time H2D" claim. (In practice, MTP drafts the next few tokens from the head's logits; the verifier then runs a forward pass for those tokens, which loads whatever KV/experts the verifier needs — but that load is the same load the no-speculation baseline would have done for those tokens, so MTP adds no *extra* load-time H2D beyond what the baseline would have done for the same tokens. A coder must ensure this — MTP must not cause extra loads beyond the baseline's loads for the same tokens.)
* `experts touched / accepted token` is reported and adapts draft width. A coder must instrument `experts touched / accepted token` (how many experts the verifier touched per accepted token — a measure of how much work the speculation saved or cost) and must adapt the draft width based on it (if `experts touched / accepted token` is high — the verifier is touching many experts per accepted token — the draft width should shrink, because the verification pass is expensive and the confidence of the draft is low; if it is low, the draft width can grow). A coder must not use a fixed draft width — the draft width adapts based on `experts touched / accepted token` (and the confidence head's stall prediction), so the engine adapts to the workload (a routing-heavy workload with many cold experts → narrow draft; a routing-stable workload with few cold experts → wider draft). A coder must report `experts touched / accepted token` (C21) and must adapt the draft width based on it.

**Worked micro-example (host, sanity-check before device):**
Implement a fake C20 with MTP (drafts tokens from the head's logits, no extra I/O), one loader for DFlash/DFlash2/DSpark with an arch compatibility check, DSpark's confidence head wired into C10 (predicts stall, stops drafting early), and the three acceptance tests. Then: (1) implement MTP as the first drafter: the head is resident (part of MODEL_DEVICE in the VRAM allocation split — `01` §3.1), so MTP drafts the next few tokens from the head's logits with no extra H2D (the head is read every step anyway — `01` §4.1: lm_head is 163 MB/token read every step, can't be amortised) — assert MTP adds zero load-time H2D beyond what the no-speculation baseline would have done for the same tokens (the loads the verifier does for the drafted tokens are the same loads the baseline would have done for those tokens) — the "MTP adds zero load-time H2D" gate; (2) implement one loader for DFlash/DFlash2/DSpark with an arch compatibility check: the loader checks the drafter's arch requirements against the target arch's caps (C2's DeviceCaps — e.g. a WMMA-based drafter on gfx1031 is refused, because gfx1031 has no WMMA — `00` §1.4) and refuses a drafter the arch cannot run — the "one loader with arch compatibility check" gate; (3) implement DSpark's confidence head wired into C10: the confidence head predicts whether the next verification pass would stall on cold experts (C9's `ready()` for the verifier's next-layer experts is false and the planner has determined it will not arrive in time — C19 would be the fallback), and if so, drafting stops early (the drafted token is not produced, because it would be discarded when the verifier stalls or falls back) — assert drafting stops early when the confidence head predicts a stall, and assert the draft width adapts (narrower when stalls are predicted, wider when they are not) — the "DSpark wired into C10, drafting stops early on predicted stall, draft width adapts" gate; (4) implement the bit-identical-to-non-speculative-under-fixed-seed acceptance: run the speculative path (drafter drafts, verifier verifies, accepted tokens survive) and the non-speculative path (no drafter, verifier runs every token) under the same fixed seed, and assert the accepted tokens are bit-identical to the non-speculative tokens (I6) — the "bit-identical to non-speculative under a fixed seed" gate; (5) instrument `experts touched / accepted token` (how many experts the verifier touched per accepted token — a measure of how much work the speculation saved or cost) and assert it is reported (C21) and that the draft width adapts based on it (high → narrow draft; low → wider draft) — the "`experts touched / accepted token` reported and adapts draft width" gate; (6) assert the drafter's and verifier's forward passes obey the "attention path only sees VRAM-resident KV" rule (I4) and the "group or die on load, no dequantise staging on the miss path (I2)" rules (C14/C15/C11/C9/C17/C18) and that the verifier's forward pass does not stall on a cold expert (the confidence head has already stopped drafting early if it would) — the "drafter and verifier obey I4/I2, verifier does not stall" gate; (7) assert the drafter's router selection is the model's router (C18 — I3) unless the drafter is a learned drafter that is itself verified (a learned drafter must be verified to produce the model's router selection, or it is not used) — the "drafter is the model's router (or a verified learned drafter)" gate.
