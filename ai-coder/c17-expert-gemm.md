# Worksheet — C17 MoE expert GEMM

**What it owns:** the other half of decode device time, and the reason any of this works.

**Why it exists (from `02-components.md` — C17 section; `01` §6; `00` §8.3/§8.9/§8.10):** the expert GEMM is `router → group tokens by expert → active expert set → waves → grouped gate/up GEMM → activation → grouped down GEMM → weighted accumulation into the residual`.
Per-token expert launches are prohibited (group or die on load). Waves: when the active set exceeds the slot pool, execute in waves and accumulate every selected expert's contribution — contributions are never dropped (I3). Weights arrive kernel-native packed from C5 — no dequantise-to-FP16 staging on the miss path (I2). The implementation split per arch is the heart of the component:

| format | gfx1201 | gfx1031 |
|---|---|---|
| W8 | WMMA i8 + scale, or dequant-to-fp16 + WMMA f16 | `v_dot4_i32_i8` inline asm — native, measured |
| W6 | unpack + WMMA f16 | `v_dot4_i32_i8` + unpack (group 64) |
| W4 (default) | unpack + WMMA f16 | **`v_dot8_i32_i4` — int4 dot consumes packed nibbles with no unpack** |
| FP8 | native WMMA f8 | unavailable |
| ternary | optional, experimental, quality-gated | optional |

**Coder notes / pitfalls:**
* Group or die on load. A coder must not launch one kernel per (token, expert). The router (C18) selects up to top-k experts per token per layer; across the batch, that is a set of (layer, expert) pairs with a count of tokens per pair. C17 groups tokens by expert (and by layer — a layer's experts are independent, but a token's experts across layers are sequential), and runs one GEMM per (layer, expert) for the tokens that route to it, accumulating into each token's residual. A coder must not do per-token-per-expert launches — that is the "per-token expert launches are prohibited" failure, and it would be transfer-bound and throughput-awful (the launch overhead alone would dominate — the whole reason the transfer-bound verdict exists is that moving the weights (181 µs for one expert at 13.6 GB/s — `00` §8.3) dwarfs the arithmetic (7.68 µs at 100% peak)).
* Waves when the active set exceeds the slot pool. A coder must implement waves: when the number of distinct (layer, expert) pairs selected in a layer exceeds the slot pool (C8), the engine executes in waves — each wave loads a subset of the selected experts into slots (C11 brings them in, C9 tracks readiness, C8 allocates slots), C17 runs the GEMM for that wave's experts for all tokens that route to them, accumulates into each token's residual, and then the next wave loads the next subset. Contributions are never dropped (I3) — every selected expert's contribution is accumulated, across waves. A coder must not drop contributions when the active set exceeds the slot pool (that is the I3 failure — "cache pressure never silently changes the selected expert set; if an expert cannot be placed, the request stalls or falls back to CPU — it does not drop" — and the waves rule is the mechanism that makes "never drop" possible when the active set exceeds the slots).
* Weights arrive kernel-native packed from C5 — no dequantise-to-FP16 staging on the miss path (I2). A coder must implement the expert GEMM to consume the packed bytes directly (C5's pack format: W4 g128 = 0.5234 B/weight = 0.5 payload + 3/128 metadata; W3 g128 = 0.3984 = 3/8 payload + 3/128; etc. — `kv_roofline.py` `pack_bytes_per_weight`, `ai-coder/operating-point.md`). The GEMM's prologue unpacks the packed weights into the form the dot instruction consumes (e.g. for `v_dot8_i32_i4` on gfx1031, the nibble-packed weights are consumed with no unpack — that is the 0.250 instr/MAC path; for `v_dot4_i32_i8` with de-interleaved activation, the weights are nibble-packed and the activations are de-interleaved — 0.625 instr/MAC). A coder must not dequantise-to-FP16 on the miss path (no "load packed bytes, dequantise to BF16, then GEMM" — that is the I2 failure; the bytes that move (C11) are the packed bytes, and the GEMM consumes the packed bytes with the minimal unpack the dot instruction needs).
* The implementation split is arch-specific and must be per-arch, not one path. A coder must implement the table verbatim: W8 on gfx1201 = WMMA i8 + scale, or dequant-to-fp16 + WMMA f16; W6 on gfx1201 = unpack + WMMA f16; W4 (default) on gfx1201 = unpack + WMMA f16; FP8 on gfx1201 = native WMMA f8; ternary on gfx1201 = optional/experimental/quality-gated; W8/W6/W4 on gfx1031 = `v_dot4_i32_i8` (and `v_dot8_i32_i4` for W4, the int4-dot-with-no-unpack path); FP8 on gfx1031 = unavailable; ternary on gfx1031 = optional. A coder must not use WMMA on gfx1031 (no matrix units — RDNA2 has none, `00` §1.4) and must not use FP8 on gfx1031 (unavailable).
* The `v_dot8_i32_i4` W4 path on gfx1031 is the "int4 dot consumes packed nibbles with no unpack" path (0.250 instr/MAC, 2.5× fewer than the `v_dot4_i32_i8` 0.625 instr/MAC path). A coder must implement it as: the weights are nibble-packed (4-bit, unsigned nibbles `u = q + zp`, same 3 B/group metadata), and the `v_dot8_i32_i4` instruction consumes the packed nibbles directly (no unpack) — that is the "zero unpack" property that makes it 2.5× fewer instructions. A coder must not unpack the nibbles before the dot (that would lose the "zero unpack" property and the 2.5× advantage). Note: this path was rejected for W4 because it needs 4-bit activations (81.5 dB SNR penalty — `00` §7.5, §8.10). So the `v_dot8_i32_i4` path is implemented (it exists, it is the 0.250 instr/MAC alternate), but it is gated on the activation precision: if the activations are 4-bit, the path is available; if the activations are int8 (the settled W4 path — `00` §7.5: "int8 activations, `v_dot4_i32_i8` with a de-interleaved activation layout"), the path is not available (it needs 4-bit activations). A coder must not use the `v_dot8_i32_i4` path with int8 activations — that is the rejection reason. The settled W4 path on gfx1031 is `v_dot4_i32_i8` with de-interleaved int8 activations and nibble-packed weights (0.625 instr/MAC), not `v_dot8_i32_i4`.
* The `_gfx12` WMMA operand layout is not 8 consecutive f16 (`00` §7.4a). A coder implementing the gfx1201 WMMA expert GEMM path must not assume the WMMA operands are 8 consecutive f16 — the builtin does not consume A as one vector of 8 halves (the one-hot-A control probe showed all eight one-hot A probes give the same D, independent of which lane was set — no 8-consecutive-f16 layout predicts that). A coder must verify the WMMA operand layout on the real device (the P1-3 A/B against the Tensile oracle is the gate for this — `00` §7.4a, `ai-coder/operating-point.md`) before building a tiled expert GEMM that assumes a layout. Until P1-3 settles the layout, the SIMT path (always compiled in — `02-components.md` C16/C17's "SIMT fallback always compiled") is the safe path, and the WMMA path is conditional on the layout being known and correct. A coder must not build a WMMA expert GEMM that assumes 8-consecutive-f16 A/B — it would read the wrong elements, silently (the same class of defect as the byte-offset-as-weight-index and page-local-vs-global bugs — `00` §7.5, §9.7.1).
* The done-when "profiler shows expert GEMM device time is not dominated by unpack arithmetic (if it is, the pack format is wrong, not the kernel)" is a real diagnostic. A coder must be able to read the C21 profiler table and tell whether the expert GEMM device time is in the GEMM math (good — the kernel is doing its job) or in the unpack (bad — the pack format is too expensive to unpack, and a different pack or a different dot instruction is needed). A coder must not ship a GEMM whose profiler shows unpack dominating — that is the signal that the pack format is wrong, not that the kernel is slow. (This is the same discipline as the expert GEMM retune story — `00` §8.9: the kernel went from 0.8% to 5.2% of peak by reducing loads per FMA (2 cols/thread), hoisting the row bound, and split-K — these are kernel/issue fixes, not pack fixes. If unpack were dominating, the fix would be a pack fix (a different pack or a different dot instruction), not a kernel fix.)
* The expert GEMM is transfer-bound, and that is the point. A coder must not spend effort optimising the GEMM's arithmetic (tiling, registers, split-K) as if that were the bottleneck — the retune story (`00` §8.9) is the lesson: the kernel went 0.8%→5.2% of peak with those fixes, but the hard ceiling at M=32 is 32% of peak (arithmetic intensity 21.3 FLOP/byte vs machine balance 66.7), and the kernel reaches 16.4% of that ceiling. Raising M is the only lever. So the expert GEMM's honest number is "5.2% of peak at M=32, 16.4% of the M=32 ceiling, and the ceiling is the limit" — not "the kernel is slow and needs more tiling". A coder must not treat the expert GEMM as the thing to optimise — the tiering work (C6/C7/C8/C9/C10/C11) is what makes the GEMM fast (by keeping the weights in VRAM so the GEMM reads them from VRAM at 589–598 GB/s, not PCIe at 13.6 GB/s — `00` §8.3: 181 µs PCIe transfer vs 7.68 µs arithmetic at 100% peak — 22×). The GEMM's job is to consume the packed weights correctly (group or die, waves, no drop, no dequant staging), and the tiering work's job is to make sure the weights are in VRAM when the GEMM needs them. A coder must keep this division clear.
